---
title: "ARES backend architecture: Django apps and request flow"
description: "ARES is built on Django REST Framework with a ViewSet-per-resource pattern. Requests flow through the DRF router, ViewSets, serializers, and ORM to SQLite."
---

ARES is a layered Django REST Framework application composed of three independent Django apps — `robots`, `sensores`, and `lecturas` — each owning its own models, serializers, and ViewSets. All three apps are wired together through a single DRF `DefaultRouter` and persist data to a local SQLite database. This separation keeps domain logic isolated while sharing a common API surface under the `/api/` prefix.

## Request flow

Every HTTP request to the ARES API passes through the same sequence of layers before a response is returned.

<Steps>
  <Step title="URL router">
    Django receives the request and matches it against `urlpatterns`. Requests under `/api/` are delegated to the DRF `DefaultRouter`, which maps the URL to the correct ViewSet and action (e.g., `list`, `retrieve`, `create`).
  </Step>
  <Step title="ViewSet">
    The matched ViewSet (`RobotViewSet`, `SensorViewSet`, or `LecturaViewSet`) handles the action. It applies permission checks, filters, and pagination, then calls the ORM to fetch or mutate data.
  </Step>
  <Step title="Serializer">
    The ViewSet delegates validation and data shaping to the corresponding serializer (`RobotSerializer`, `SensorSerializer`, or `LecturaSerializer`). On writes, the serializer validates the incoming payload before saving. On reads, it converts model instances to Python dicts.
  </Step>
  <Step title="ORM and SQLite">
    Django's ORM translates the serializer or ViewSet operation into a SQL query against the SQLite database. The query result is passed back up the chain and the serializer renders it as JSON in the HTTP response.
  </Step>
</Steps>

## Application structure

Each Django app owns a single domain entity and is fully self-contained.

<AccordionGroup>
  <Accordion title="robots" icon="robot">
    Manages the robot fleet. Owns the `Robot` model, `RobotSerializer`, and `RobotViewSet`. The `Robot` model stores identity, operational status, and GPS coordinates. All sensors belong to a robot via a foreign key.
  </Accordion>
  <Accordion title="sensores" icon="microchip">
    Manages sensors attached to robots. Owns the `Sensor` model, `SensorSerializer`, and `SensorViewSet`. Each sensor records its type and measurement unit and holds a foreign key to its parent `Robot`.
  </Accordion>
  <Accordion title="lecturas" icon="chart-line">
    Manages individual sensor readings. Owns the `LecturaSensor` model, `LecturaSerializer`, and `LecturaViewSet`. Each reading captures a numeric value, a timestamp, a processing flag, and a foreign key to its parent `Sensor`.
  </Accordion>
</AccordionGroup>

## URL routing

The three ViewSets are registered with a single `DefaultRouter` in `ares_backend/urls.py`:

```python ares_backend/urls.py
from rest_framework.routers import DefaultRouter
from django.urls import path, include

router = DefaultRouter()
router.register(r'robots', RobotViewSet)
router.register(r'sensores', SensorViewSet)
router.register(r'lecturas', LecturaViewSet)

urlpatterns = [
    path('admin/', admin.site.urls),
    path('api/', include(router.urls)),
]
```

`DefaultRouter` automatically generates the full set of standard REST URLs for each registered resource. For example, registering `robots` produces:

| Method | URL | Action |
|--------|-----|--------|
| GET | `/api/robots/` | list |
| POST | `/api/robots/` | create |
| GET | `/api/robots/{id}/` | retrieve |
| PUT | `/api/robots/{id}/` | update |
| PATCH | `/api/robots/{id}/` | partial_update |
| DELETE | `/api/robots/{id}/` | destroy |

The same pattern applies to `/api/sensores/` and `/api/lecturas/`.

## Data persistence

ARES uses SQLite as its default database backend, configured in `ares_backend/settings.py`:

```python ares_backend/settings.py
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}
```

The database file is stored at the project root as `db.sqlite3`. SQLite requires no additional server process and is suitable for development and single-node deployments. For production environments with concurrent write load, replacing the engine with PostgreSQL or MySQL is recommended.

<Note>
  The Django admin panel is available at `/admin/`. It provides a web interface for browsing and editing all model instances without writing any code. Access requires a superuser account created with `python manage.py createsuperuser`.
</Note>
